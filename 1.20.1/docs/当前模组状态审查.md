# 当前模组状态审查

> 本文是 v0.10.0 审查基线。v0.11 已重构运行与存储边界，并针对下述问题增加正确行为回归；现状与剩余限制见 [重构报告](底层抽象与运行边界重构.md)。保留原始数据供对照。

日期：2026-10-29。对象：v0.10.0，Minecraft 1.20.1 / NeoForge 47.1.106 / JDK17。分支 `codex/minecraft-state-audit`。本次保留发布运行代码与JAR，只增加审查报告和独立复现实验；未暂存、提交、合并或推送。

**结论：已有可玩的基础沙盒循环，但可靠性存在阻断，不能认定为完整闭环或已通过高效运行验收。** 单杖小法阵的核心开销较低，规模扩大后，完整状态序列化和逐点粒子广播成为明显负担。新发现的大载体/大卷册真实二进制存储丢失应先处理。

## 玩法闭环

| 环节 | 当前判断 | 依据或缺口 |
|---|---|---|
| 获取物品、部件和基板 | 可达 | 使用原版材料与工作台配方；书籍、部件、设备均有生存配方 |
| 绘制、保存、启动、实际世界效果 | 基本成立 | 逐步VM、有限玩家魔力、真实火/水/光/暗/奥术作用、命中派生已接通 |
| 杖端/身/尾与磨损修缮 | 成立 | 独立工作台扣料换件、回收旧件、保留磨损，修复也实际扣料 |
| 书籍归档与多阵切换 | 功能已接通，保存不可靠 | 书自身持有法阵；大程序集或大卷册的NBT字符串写盘会丢失，见P1-1 |
| 互联、停供与回收 | 正常路径成立，异常收尾缺失 | 残余和在途有账本；一端真正丢失后，另一端无法拆线/回收，见P1-3 |
| 固定设备长期使用 | 部分成立 | 有限充能、已加载区块运行；所有者离线或进入另一维度就停止推进，不是独立自动化设备 |
| 战斗中快速换法术 | 可用但步骤多 | 翻页只换启动目标，不停原阵或启动新阵；持续施法换阵需“停旧阵→翻页→起新阵”，否则旧阵继续耗魔 |
| 成长和反复游玩 | 需要实际生存体验验证 | 目前侧重自主搭阵；符文全目录可用，升级主要靠材料/部件。原版探索与战斗提供用途，但尚未验证新手引导、数值收益和长期工程需求 |

没有独立Boss、研究树或任务并不等于沙盒玩法有错误。当前更需要验证“玩家为何选择这一种阵、资源投入是否值得、失败后能否恢复”，不应先靠新增系统掩盖保存和回收缺口。

新手起步还有一个应明确的设计选择：法杖合成只接受石英杖端，法杖工作台本身也要石英；铜制/紫晶杖端不能直接作为第一根法杖的合成替代品。若希望前期主世界即可接触法术，应调整起步路径；若刻意把石英作为门槛，则需要在游戏内解释。配方存在不能替代新手首次完整体验。

## P1-1：合法的大卷册和法阵组在实际NBT写入时丢失

位置：`server/BookService.java:18`、`server/CarrierService.java:43`、`adapter/JsonCodecs.java:99`及`:110`。

两个载体分别把整个配置/现场JSON写进单个 `StringTag`。本地目标版本的 `StringTag.write` 实际调用 `DataOutput.writeUTF`，单字符串采用modified UTF-8，最多65535字节；超限捕获异常、记录 `Failed to write NBT String`，随后写入空字符串。模组卷册允许512KiB，程序集读取允许1MiB，均没有在写NBT前约束或改变存储方式。

实际服务器复现：

| 合法输入 | 原JSON字符数 | 压缩NBT写入再读出 | 结果 |
|---|---:|---:|---|
| 16页蓝图簿，每页64符文 | 130624 | 0 | 内容丢失 |
| 4槽载体，每槽64符文、0线路 | 61103 | 61103 | 本例仍未超界 |
| 4槽法术书，每槽64符文、64条相邻信号线 | 87983 | 0 | 全部程序集丢失 |

后一个例子同时经过真实 `FriendlyByteBuf.writeItem/readItem`：接收端的 `Assembly` 也变成0字符。本例都是ASCII JSON，字符数即相关编码字节数；中文页名还需要按modified UTF-8处理，不能只判断Java字符串长度。

前版 `ItemStack.save → ItemStack.of` 只在内存NBT树内往返，没有编码到字节，因此仍能通过。这解释了此前“完整NBT恢复”测试的覆盖缺口。重新加载空串后校验会拒绝，不会凭空恢复原法阵；“保留损坏记录”无法恢复已经被写空的内容。

建议：将程序集与卷册改为有版本的结构化NBT或有长度上限的字节数组存储，显式读取旧String格式；在完整验证和编码成功后再替换数据。增加压缩NBT文件与物品网络的真实字节往返回归，覆盖合法容量上限、中文及运行缓存增长。不能仅把容量静默降低到少量页面来声称解决原目标。

## P1-2：全部待机的法杖仍每步完整序列化

位置：`server/WorldCircuits.java:56`、`server/CarrierService.java:43`、`server/ServerEvents.java:15`。

法杖库存tick总是入队。世界收尾无条件把每个载体的全部槽位、完整蓝图及所有运行数组转为JSON并写NBT；每根法杖又重复保存同一玩家槽。固定法阵也每步标记改变。即使 `active()==false`、没有输出或配置变化，这条保存路径仍执行。

实测隔离服务器入口，每杖4槽、每槽64个信号符文、0条线，所有法阵停供：

| 法杖数 | 第一轮中位ms/步 | 第二轮中位ms/步 | 第二轮P95ms/步 |
|---:|---:|---:|---:|
| 1 | 3.333 | 1.215 | 2.412 |
| 4 | 6.468 | 4.821 | 8.355 |
| 16 | 17.740 | 15.428 | 19.453 |
| 36 | 40.449 | 29.588 | 34.117 |

两轮是本机短时采样，受预热/JIT和系统负载影响，不是稳定基准。它们都显示：一个满背包的复杂待机法杖就占用相当部分50ms服务器步预算，这还没有算Minecraft其余世界、实体、真实施法和网络。

独立核心探针中，36件同类载体仅序列化每步约分配16.1MiB（按20Hz约322MiB/s）；待机仍有明显GC压力。相较之下，单件空白单槽JSON序列化约0.045ms，16符文单槽约0.110ms：小规模可用，不能从这些数值外推出大规模高效。

注意：待机时写入的字符串内容相同，不代表原版一定每步发网络包；这里确认的是CPU和分配浪费。活动现场改变时共享NBT还可能携带完整JSON，真实压缩联网带宽本次未量测。

建议：活动载体调度和持久化分别判脏；冻结蓝图复用，避免每步重复生成；玩家槽按玩家每边界至多处理一次。保存、丢弃、所有权变化和容器移动前建立明确的最新现场同步点，不能用降低保存频率换取现场丢失。

## P1-3：互联一端丢失后，没有可完成的断线与回收路径

位置：`server/WorldCircuitLinks.java:32`、`server/ServerEvents.java:24`、`block/CircuitBlock.java:40`。

普通玩家拆块会先检查互联引用。但一端通过非玩家方块移除路径销毁时，世界线路与锚点仍保留；`disconnect` 强制两端都存在、已加载且归玩家所有。实测连接两块后调用服务器 `destroyBlock` 移除源端：接收端仍被引用，断线报“两端须已加载且归你所有”；剩余端的回收同样被引用检查拒绝。

若原载体仍能回收并放回原锚点，可恢复两端后再拆线；若它永久丢失，当前操作没有收尾入口。此时恢复闭环不成立。实验未声称覆盖所有爆炸和第三方破坏路径，但已确认一种原版服务器非玩家移除路径。

建议：区分“暂时卸载”和“确认销毁”，持久化线路所有权并提供合法的悬挂连接恢复操作；对在途资源明确回收、转移或记损耗，不能简单删线丢账，也不能允许任意玩家强行断别人的线路。

## P2：表现网络按粒子点广播，规模上限下成本过高

位置：`server/SpellEffects.java:133`、`server/WorldSpells.java:110`。

光束每0.25格独立调用一次 `sendParticles`，64格最多257次。每面屏障每步广播12个点，64面上限对应每秒15360次广播调用。本地编码的该粒子包体46字节；对在接收范围内的单个观察者，满屏障场景仅这些包体理论约690KiB/s，尚不含协议开销和其他表现。没有观察者时不会等价地产生该网络流量，所以该数值是代码上限估算，不是联机实测。

建议：服务器只同步光束端点/元素及屏障创建、状态改变和移除；客户端按这些结果绘制整条光束/整面盾，设置可见距离与表现预算。权威命中、容量和寿命继续在服务器推进。

## 设计边界与当前验收

固定设备的推进入口 `WorldCircuits.java:27` 要求所有者在线且当前维度一致。即使区块由其他玩家保持加载，所有者进入下界后设备也暂停。它是当前已记录的实现边界，并非本次发现的未说明存档错误；但它限制了“固定阵作为独立自动化设施”的玩法闭环。应明确保留这个规则还是把运行与在线玩家实体解耦。

既有结果为73950项核心断言、59项正常GameTest及61张界面交互截图。本次重新运行59项正常GameTest，并临时注入4个审查探针：总计63项执行完成，正常回归通过，探针确认上述缺陷及性能数据。探针通过的含义是“问题确实出现”，不能作为健康验收。真实NBT超限的ERROR在本次属于预期复现结果，不能用“日志无ERROR”概括。

没有重复做无关的Godot回归或GPU截图，也没有做实际新玩家完整生存试玩、长时TPS/GC、粒子密集世界GPU帧率或真实多人压缩带宽验收。以前的编辑器无世界短测证明了该路径优化有效，不能代表完整世界运行高效。

复现实验见 `tools/audit/README.md`；原始日志为 `build/audit/core-final.log`、`server-final.log`，第一轮对照日志也保留。发布JAR仍为496590字节、SHA-256 `3b609392aca7520f8917d716d03c488f84590138c5f03be934c22a849e651fdf`，没有把审查当作修复发布。

优先顺序：**先修真实存储与网络往返 → 补齐丢失端点的收尾 → 消除待机全量序列化 → 改为客户端绘制整段表现 → 再做一轮新建生存世界的完整体验和规模性能验收。**
