# 代码质量与运行开销审查 · 0.49.0

日期：2026-11-04。范围为Minecraft 1.21.1工程，审查302个生产Java文件的模块结构，并重点阅读VM、调度、物品仓储、返还、魔力场、网络观察、编辑器和特效生命周期。分支 `codex/runtime-quality-audit`；未暂存、提交或推送。

## 判断

当前具备可继续迭代的工程基础：领域/应用层与Minecraft适配分离，固定步拥有权明确，静态图集和视觉预算已接入，完整快照、坏数据保留、来源返还及架构依赖都有回归保护。但还达不到“质量和性能都已完善”的程度。部分轻量查询仍复制大记录，已完成任务仍占活动预算，编辑器存在固定占位编号与稀疏编号边界问题，几个核心类也仍然承担过多职责。

这次依据可复现行为修改局部路径，保留固定步执行顺序、施法公式、存档格式、网络格式和返还防重记录。

## 已修复与优化

| 问题 | 影响 | 修改 |
| --- | --- | --- |
| 法杖部件查询多次 `ItemData.read` | 每次复制整个自定义NBT，包括可能很大的法阵编码；固定阵供能和装备触发也有同类路径 | `ItemData.section`通过原生Codec读取并复制指定小节，缺失返回独立空值，错误类型拒绝；完整写入仍走原来的不可变组件边界 |
| 符文编号取 `max+1` | 导入含Integer.MAX_VALUE编号的合法法阵后无法再放置符文 | 选择最小未使用正编号；已有编号和线路不改写，撤销/重做保留 |
| 线路预览使用固定目标编号1025 | 源符文恰为1025时预览构造出自连接，合法线路显示非法 | 只为损耗提示选择与源不同的临时编号，不加入实际蓝图 |
| 历史完成返还仍参与每步轮转 | 记录越多，真正未结清的返还等待越久；还反复查找接收源和分配列表 | 持久表保留全部去重凭据，活动索引仅包含未结清项；结清后移出活动索引，恢复时从账本重建 |
| 返还恢复依赖来源列表排列 | 与接纳时的规范顺序不一致，重试可能误报金额冲突 | 恢复按来源键排序，拒绝不可能由正常接纳生成的空来源列表；离线/部分完成继续保留 |
| VM接口查询线性扫描全部符文 | 多条跨阵接口反复查找，开销随节点数增长 | 定义冻结时建立编号索引；查询平均O(1)，不改变符文执行顺序 |
| 每个分流符文重复遍历全部线路 | 大蓝图校验在分流较多时为O(S×E＋P)，拖动预览也会调用 | 在线路校验过程中按原线路顺序统计权重，变为期望O(V＋E＋P)，其中P是线路路径格总数 |
| 每个渲染帧复制活动特效列表 | 高刷新率下重复复制同一逻辑步的最多2048个观察 | 时间线改变时失效，下次读取发布不可变列表；同一步复用，历史列表不反写 |

活动返还索引保持持久凭据的插入顺序，只移除结清项，因此无需新增存档字段。尚未返还的离线来源继续轮转；完成的去重记录仍计入总凭据预算，达到预算仍明确背压。这次没有擅自删除收据或声称解决长期存档无限增长问题。

## 剩余工作与边界

1. `TickCircuit`约62 KB，混合供给、控流、转运、存储、失败返还和恢复校验；`JsonCodecs`约44 KB集中多个协议；`WorldSpells`约42 KB混合弹道、屏障和持久化。后续应分别抽出编译拓扑/协议读取器/法术状态存储，并保持VM单一状态所有者，避免拆成共享可变状态的辅助类。
2. `CircuitScreen`约45 KB仍集中输入、控件装配和子页导航；在完整回归保护下继续按参数表单、导航、侧栏拆分更有价值。这里的KB为源文件字节量，包含中文，不代表运行内存。
3. 新增部分模块仍通过静态Minecraft服务互相调用，构造依赖与生命周期清理不完全显式。异常分支也有静默捕获；需逐项区分预期坏数据隔离与真正实现错误，不能统一删除catch或在每tick重复打印日志。
4. 返还历史记录与接收收据必须保留防重；长期服务器还需要有明确安全前提的归档/压缩协议。不同玩家、区块与SavedData仍分文件落盘，不具备断电场景的数据库级原子事务。
5. 魔力场和固定阵观察虽然有活动集合/数量预算，仍有全表维护与排序；高实体密度、多玩家和大规模法阵的JFR/GC、TPS与带宽采样尚未完成。此次不贸然加入多线程，不让并发破坏确定性和Minecraft线程约束。
6. 编译仍有NeoForge事件订阅旧API弃用警告。应按本地平台接口做后续迁移验证；这不影响本次构建通过，也不应被写成“零警告”。

当前结论：本次消除了数处有证据的分配浪费和队列/编号问题，核心模块仍值得继续做小步职责拆分；现阶段不能宣称已经完成全量性能验收。
